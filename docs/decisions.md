# Decisions and Open Questions

A short record of what has been decided, why, and what is still open. Update it when something changes. The research behind each decision is in the files named below; nothing in them was tested live.

**Companion documents:** `prd.md`, `development-plan.md`, `workflows.md`, `design.md`.

---

## Decided (2026-10-12)

| Area | Decision | Why | Research |
|---|---|---|---|
| Compute | One AWS EC2 t4g.small with an Elastic IP, Dockerized (Go app, Caddy, Postgres) | Keeps the Go binary and the Postgres schema unchanged. About $16/month with the public IP. | `aws.md` (shape 1A/1B) |
| Database | PostgreSQL on the same instance, data on its own EBS volume. Nightly `pg_dump` to S3 plus daily EBS snapshots. | Cheapest. A managed database (RDS, about +$25/month) costs more than the compute. | `aws.md`, `flat-file-json.md` (database-first, files only as derived artifacts) |
| Email | Amazon SES, a la carte pricing, one region, two streams (`auth.` and `mail.`), bounces and complaints through SNS | About $0.10 per 1,000, the cheapest option that passes the must-haves (own unsubscribe headers, no tracking, per-message From name). | `email.md` |
| CDN and custom domains | Stay on BunnyCDN | No rewrite of the purge client or the custom-domain lifecycle. Bunny can front an AWS origin. | `bunny.md`, `aws.md` |
| Uploads | Private S3 bucket, served by the app on the visitor's hostname | A white-label domain must not show a storage provider's hostname. | `aws.md` |
| Visual design | Clean is the default look for every group and the platform. Any group, free or paid, can choose Lively, Confetti or Poster. Brand color and logo stay paid. Noticeboard and Program were dropped. | Clean was the preferred direction. The others give every organizer a distinct, colorful identity. The look is its own column, so it survives a lapse; color and logo reset. | Design treatments page (published artifact) |

## Working decisions (2026-10-15, not finalized)

| Area | Decision | Why | Notes |
|---|---|---|---|
| Referrer-Policy on token pages | `same-origin`, not `no-referrer`, on `/auth/verify/{token}`, `/rsvp/cancel/{token}` and `/unsubscribe/{token}` (replaces the value in `development-plan.md` route category 4 and `prd.md` §6). | Under `no-referrer` a browser sends the page's own form POST with `Origin: null` and no Referer, so Rule 5's Origin check would refuse the confirm buttons and no magic-link login could complete. Accepting `Origin: null` would switch CSRF protection off (any page can make a browser send it) and reopen login CSRF. `same-origin` sends the token URL only back to our own site, which already has the token; other sites, links and map embeds never see it. | Owner chose option A on 2026-10-15. Alternatives rejected: exempting token routes from the Origin check (login CSRF), a second CSRF-token mechanism. |
| Origin check (Rule 5) details | On every POST and DELETE not declared exempt: if `Origin` is present its host[:port] must equal the current host (`null` fails); if it is absent the `Referer`'s host[:port] must; if **neither header is present the request is refused**. Only host and port are compared, never the scheme (TLS ends at the CDN and Caddy). Comparison is by parsed host equality, never prefix or substring. A refused request gets `403 Forbidden`, `Cache-Control: no-store, private`, and the same plain-text body on every host with no platform or group name ("This request didn't come from this site. Go back, reload the page and try again."); the app logs a warning with host, method, path, Origin and Referer. | Literal reading of Rule 5 ("the origin must equal the current hostname"), failing closed. Every current browser sends `Origin` on POST/DELETE, so refusing header-less requests costs real users nothing. | Owner confirmed refusing header-less requests on 2026-10-15. The one-click unsubscribe POST from mail apps needs its own exemption (Phase 6 question). |
| Client IP (Rule 8) | The app trusts a forwarded header only when its immediate peer is in `TRUSTED_PROXIES` (Caddy's address; empty in dev, so dev always uses the peer). It reads only `CLIENT_IP_HEADER` (default `X-Forwarded-For`) and ignores every other forwarding header. It takes the **rightmost address in that header that is not itself a trusted proxy**. A missing, empty or malformed header falls back to the peer address. | Every production request reaches the app through Caddy, and ports 80/443 are open to direct callers (SNS, Stripe, attackers), so "from the origin proxy" alone can't tell a CDN-set header from a forged one. The leftmost entry is whatever the caller wrote; the rightmost untrusted entry is what our own infrastructure recorded. | Owner agreed 2026-10-15. Caddy's part (trusting Bunny's published edge ranges so a direct caller can't inject an address) is settled in the Phase 9 spike with live Bunny, like `HOST_SOURCE`. |
| Host matching | The visitor hostname is lowercased, then must equal `PUBLIC_HOST`, `ORIGIN_HOST` or an active custom domain exactly, port included (`localhost:8080` in dev). A trailing dot (`meet.space.`) or an explicit default port (`meet.space:443`) is not tidied up: it gets the same 404 as an unknown host. | Hostnames are case-insensitive (DNS), and browsers already lowercase them. Browsers treat `meet.space.` as a different site (own cookie jar, different `Origin`), so accepting it would give a half-working copy where logins don't stick and forms are refused. | Owner agreed 2026-10-15. |
| `HOST_SOURCE` header edge cases | When `HOST_SOURCE` names a header: present once with a single value → use it (lowercased, matched exactly); missing → fall back to `Host`; repeated, or containing a comma → unknown host, 404. When `HOST_SOURCE=host`, `X-Forwarded-Host`, `Forwarded` and every other host-ish header are ignored. | SNS and Stripe call `origin.meet.space` directly, without the CDN header, and must still reach `/webhooks/*` and `/health`. In header mode Caddy serves only the origin site block, so the fallback can only resolve to the origin. Several values can't be trusted, so the app doesn't guess. | Owner agreed 2026-10-15. Which mode is used comes from the Phase 9 spike. |
| `/health` | Served on `ORIGIN_HOST` only (404 on the platform, custom domains and unknown hosts). `200`, plain text `ok` when the database ping succeeds within 2 seconds; otherwise `503`, plain text `database unavailable`, with the error only in the log. Always `no-store, private`. | Monitoring calls the origin directly. Serving it on every domain would expose a database-status signal on white-label domains for no user benefit. | Owner agreed 2026-10-15. A container-internal health check (Phase 12) must send `Host: origin.meet.space`. |
| Error pages | **Platform:** platform layout; 404 "We can't find that page." with "Go to the home page" → `/`; 500 "Something went wrong on our side." with "Try again". **Active custom domain:** the same, in the group's own layout (name, color, no platform marks); "unbranded" in design.md §6 is read as "no platform branding". **No site** (unknown host, `pending_dns` domain, origin paths other than `/health` and `/webhooks/*`): a bare "Page not found." with no name, no layout and no link. **htmx fragment requests:** the one-line message only, so it fits inside the box htmx 4 swaps it into. Always the right status, `no-store, private`, no stack traces or error details (log only). | One message, one way out (design.md §6); white-label (prd.md §4.3). A pending domain is the customer's own hostname, so the platform name must not appear there either. | Owner agreed 2026-10-15. |
| Cookie on a cacheable response | If a response from a route declared cacheable (a public page or an immutable file) carries `Set-Cookie`, under any spelling of the header, it is sent `Cache-Control: no-store, private` instead and the app logs an error with host, method, path and status. The cookie still goes out. No-store responses that set cookies (logins, RSVPs) are normal and log nothing. | A cached `Set-Cookie` would hand one visitor's cookie to everyone the CDN serves that copy to. A test already checks that no cacheable page sets a cookie for any role; this is the backstop for a future bug the tests miss, and the error log makes the bug visible. Stripping the cookie would hide the bug and could break whatever set it; a 500 would take the page down. | Owner agreed 2026-10-16. |
| Outbox retry schedule | After a temporary send failure, the outbox waits and tries again on a schedule for each stream. **`auth`:** 10 s, 30 s, 1 min, 2 min, 5 min (about 9 minutes in all). **`notify`:** 1 min, 5 min, 15 min, 1 h, 4 h, 12 h (about 18 hours in all). Each wait varies by about ±20%. When the last retry fails the row becomes `dead`, keeps its `last_error`, and is never sent. | Login links expire 15 minutes after they are made (prd.md §3), so the last `auth` retry still lands inside the link's life. Notifications are still worth delivering hours late; 18 hours means even a 24-hour reminder that fails every retry would land about 6 hours before the meeting. The variation stops a batch that failed together from retrying all at once. A dead row stays visible to the Phase 12 alert on old unsent rows, and someone whose login email died can ask for another. | Owner agreed 2026-10-16. The numbers are constants, easy to tune after launch. |
| Outbox rows stuck in `sending` | Taking a row to send counts as an attempt (`attempts` goes up), sets `status = 'sending'`, and sets `next_attempt_at` 2 minutes ahead: a 2-minute claim. Each call to the mail provider times out after 30 seconds, so a live send never outlasts its claim. A row still `sending` when its claim runs out counts as a failed try and follows the retry schedule above; when its tries are used up it becomes `dead`. The same for both streams. `idx_outbox_due` therefore also covers `'sending'` (development-plan.md's DDL updated to match). | Covers a crash and a hung send alike. The plan already accepts its worst case, one duplicate email when the provider took the message but the row was never marked `sent`; 2 minutes is the plan's "short delay" before an `auth` row is retried. Counting the attempt when the row is taken means an email that crashes the server every time runs out of tries instead of looping forever. Resetting rows at startup would leave a hung send stuck until a restart; never retrying would lose login links. | Owner agreed 2026-10-16. Permanent send errors are a separate question. |
| Outbox permanent send errors | The `Sender` marks each error **temporary** or **permanent**. A permanent error (the provider rejects this message or address) makes the row `dead` at once, keeping `last_error`, with no further tries. Everything else is temporary and follows the retry schedule, including account-wide errors (account paused or suspended, sending domain not verified); those are also logged at error level. There is no account-wide stop: each row still expires on its own schedule. | Ends hopeless sends at once. During an account-wide outage every row still runs out of tries on schedule, so nothing stale (a reminder for a meeting already past) piles up to go out when the account returns. The failed calls in an outage cost nothing and are capped at the notify rate. The plan's Phase 6 guard already stops the poller before bounce or complaint rates approach the provider's limits. | Owner agreed 2026-10-16. Phase 0 has only the dev sender and the test fake; the SES errors are mapped to temporary or permanent in Phase 6. |
| What Enqueue checks | Enqueue refuses the email (returns an error, writes nothing, so the caller's transaction rolls back) if: the recipient is not one plain address (no display name, lowercase); the From display name, subject or any header value contains a line break or other control character; a header is not `List-Unsubscribe`, `List-Unsubscribe-Post` or `Reply-To`; the stream is not `auth` or `notify`; or the kind or dedupe key is empty. Bodies are not checked here. | An email header ends at a line break, so a value carrying one can add headers of its own (a `Bcc` to thousands). The forms validate what people type, so a refusal here is a bug in our code; failing closed and loudly is safer than sending a cleaned-up or unchecked message. Whether SES itself would reject such values is live-only and unproven. | Owner agreed 2026-10-16. Which addresses count as valid (non-ASCII) waits for its own question; until then the check accepts plain ASCII addresses. |
| How soon a queued email is sent | Enqueue runs `NOTIFY` on an outbox channel inside the caller's transaction; Postgres delivers it only on commit. The poller holds one connection that `LISTEN`s and starts sending as soon as a notification arrives. It also checks every 5 seconds, which picks up retries that have come due, expired claims, and any lost notification. Retries therefore go out within about 5 seconds of their due time. | A login email starts sending the moment its transaction commits, and the database guarantees the poller can't wake before the row is visible, so no caller has to remember to signal. Polling alone adds up to a second (or more) of delay to every login link; an in-process signal relies on each caller nudging after commit and misses rows queued by other commands. | Owner agreed 2026-10-16. Costs one held database connection. |
| Security headers | Every response the router sends, on every host and status, carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`. They are set just before the status line, like `Cache-Control`, so a handler can't drop or change them. No site, including our own, can show a meet.space page in a frame. HSTS and a full Content-Security-Policy are not set yet. | `nosniff` stops a browser from treating an uploaded file (Phase 7, served from the group's own host) as a page and running its script there. The framing ban stops clickjacking: another site loading a page invisibly and tricking a visitor into pressing a real button (confirm login, cancel RSVP, delete). The docs never mention embedding; a narrow exception for read-only pages can be added if a group asks for it. | Owner agreed 2026-10-16. HSTS waits on how Bunny terminates TLS (Phase 9 spike) and on what is safe for customers' own domains; a full CSP waits on the scripts later phases add. |
| Reply rules in the database | Postgres itself refuses a reply whose parent is not a feed post in the reply's own group (so no reply to a reply, no reply on a meeting comment, no cross-group reply), and a meeting comment on another group's meeting, on insert and on update. Done with composite foreign keys: `posts` gains two stored generated flags (`is_feed_post`, `is_reply`) and `UNIQUE (id, group_id, is_feed_post)`; `posts_parent_fkey` is `(parent_id, group_id, is_reply) → posts (id, group_id, is_feed_post)` and `posts_meeting_fkey` is `(meeting_id, group_id) → meetings (id, group_id)`, both `ON DELETE CASCADE`. `meetings` gains `UNIQUE (id, group_id)`. development-plan.md's DDL updated to match. | workflows.md §7 says these replies are "rejected by the server and the database", and the reply route requires "a feed post in this group"; the plan's DDL only stopped a comment from having a parent. Keys, not triggers, are how the rest of the schema enforces its rules, and Postgres checks them on every write, whatever code path does it. | Owner agreed 2026-10-16. |
| No triggers | The schema has no triggers. Every rule the database enforces is a constraint, key, CHECK or unique index. A test fails if a trigger appears. | Owner: "I can't see a reason to have any triggers." Triggers hide logic away from the schema the rest of the rules live in; the plan already avoids them for `updated_at`. | Owner, 2026-10-16. |
| One owner per group | Each group has exactly one owner, split between two layers. **The database** refuses a second owner (`idx_one_owner_per_group`, unchanged). **The server** keeps at least one: it creates a group and its owner membership in one transaction; it transfers ownership in one transaction (demote the old owner first, then promote the new one); it refuses to let the owner leave, demote or remove themselves; and it refuses to delete the account of someone who owns a group (workflows.md §14). prd.md §7 and workflows.md §9 reworded to match. Co-owners are not supported. | Keeps the plan's role model and schema as they are. One owner fits billing (the payer is the person who entered the card, and a transfer hands the subscription over), and the owner-only powers (delete, transfer, domain, branding, co-organizers) would clash between equals; co-organizers already share day-to-day management. Having the group point at its owner (a key checked at commit) was the alternative; it would make co-owners harder to add later. | Owner chose this on 2026-10-16. Risk accepted: a server bug or manual database edit could leave a group with no owner. The platform admin can't yet reassign a stranded group; raise that when the admin pages are built. Each "at least one" rule is tested in the phase that builds it. |
| HTMX version | htmx 4.0.0, vendored as `static/js/htmx.min.js` | Owner preference. Pages no longer go into a `localStorage` history cache (htmx 4 reloads the full page on back), so private fragments are never written to storage. | npm still tags 2.x as `latest`; 4.0.0 is the GitHub "latest" release. The plan's htmx patterns are written for htmx 2. In htmx 4: attribute inheritance must be explicit (`hx-target:inherited`); 4xx/5xx responses swap by default (use 422 for inline form errors, `hx-status:` per element); `hx-delete` no longer sends the enclosing form's inputs; event names are colon-separated (`htmx:after:swap`). `HX-Trigger` responses and `hx-trigger="load, rsvp-changed from:body"` work unchanged. |

**Consequences of the choices above**
- No high availability. An instance failure means restoring from the latest backup; the worst case is losing up to a day of data until WAL archiving is added.
- AWS bills for the public IPv4 address ($3.65/month) whether or not it is in use.
- SES enforcement is account-wide: a bounce or complaint problem in one group can threaten sending for every group. The plan therefore pauses bad groups automatically and keeps login mail on its own stream.
- SNS and Stripe call the origin directly, so ports 80/443 can't be limited to the CDN's IP addresses.

## Known gaps the plan accepts

- Anonymous RSVP email addresses are unverified. A typo sends a confirmation to a stranger. Mitigations are in Phase 2 (limits, MX check, no echoed free text, suppression).
- Custom domains must be added by hand to the Google Maps browser key's allowed websites until the Google API Keys API is automated (Phase 10).
- Apex domains need CNAME flattening at the customer's DNS provider. Owners are told to use a subdomain.
- Every group's complaints share one sending reputation. Per-group sending domains are deferred.
